# ORCA Backend - Object Reconstruction via Photogrammetry

FastAPI backend that turns a set of overlapping photos of an object into a 3D mesh
using COLMAP (Structure-from-Motion + Multi-View Stereo), Poisson meshing, Open3D
clean-up and a mesh quality report. Jobs are queued in Supabase and processed by a
worker, so the API stays responsive.

## How a job flows

```
POST /jobs/                      -> job CREATED
POST /upload/image/{id}          -> images validated + saved, job UPLOADING
POST /jobs/{id}/start            -> job PENDING (returns 202 immediately)
worker claims the job            -> PROCESSING   (stage + progress are updated)
   sfm      COLMAP features, matching, mapper; best model chosen; registered-image gate
   dense    undistort, PatchMatch, fusion, Poisson (retry at lower depth)
   mesh     Poisson mesh, else Ball-Pivoting on fused.ply; clean-up; decimation
   quality  PASS / WARN / FAIL report
-> COMPLETED  (or FAILED with a stored reason, stage and error code)
GET /jobs/{id}                   -> status, stage, progress, error, quality summary
GET /jobs/{id}/result            -> list of downloadable files
GET /jobs/{id}/result/download?file=final_mesh.ply
```

State changes are validated against one transition table and applied atomically
(`app/jobs/job_states.py`, `JobRepository.transition`). Every change is written to
the `job_events` table.

## Setup

Requirements: Python 3.10+, [COLMAP](https://colmap.github.io/) built with CUDA, an
NVIDIA GPU (dense reconstruction needs CUDA), a Supabase project.

```bash
python -m venv .venv && source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env                                    # fill in the Supabase values
```

1. In Supabase create the storage bucket `orca-images` and the tables `jobs`
   (`job_id uuid`, `method`, `status`, `created_at`, `updated_at`) and `images`
   (`id`, `job_id`, `image_path`, `uploaded_at`) if you do not have them yet.
2. Run **`schema.sql`** in the Supabase SQL editor. It adds stage, progress, failure
   reason, result and audit-trail columns. The backend still runs without it, but
   cannot then show stage, progress or failure reasons.
3. Tell ORCA where COLMAP is: put `colmap` on PATH or set `COLMAP_BIN` in `.env`.

## Run

```bash
uvicorn app.main:app --reload        # API + embedded worker (default)
```

Docs: http://127.0.0.1:8000/docs - health: http://127.0.0.1:8000/health

To run the worker as its own process (recommended on a server):

```bash
EMBEDDED_WORKER=false uvicorn app.main:app
python -m app.workers.local_worker
```

Run **one** worker per GPU. On start-up the worker requeues jobs that were left in
`PROCESSING` by a crash (up to `MAX_JOB_ATTEMPTS`), which would steal a job from
another live worker.

Run the whole pipeline on a folder of photos without HTTP:
`python -m scripts.run_pipeline_local path/to/photos`

## Endpoints

| Method and path | Purpose |
|---|---|
| `POST /jobs/` | create a job (`method_1` only; `method_2` returns 501) |
| `GET /jobs/{id}` | status, stage, progress, error, quality summary |
| `POST /upload/image/{id}` | upload photos (JPEG/PNG/TIFF; validated, all-or-nothing) |
| `POST /jobs/{id}/start` | queue the job (202) |
| `GET /jobs/{id}/logs?tail=200` | tail of the job log |
| `GET /jobs/{id}/events` | state-change audit trail |
| `GET /jobs/{id}/quality` | full quality report |
| `GET /jobs/{id}/result` | downloadable files of a completed job |
| `GET /jobs/{id}/result/download?file=` | download a whitelisted file |
| `GET /health` | COLMAP, CUDA, disk, Supabase (503 when something is missing) |

## Upload rules

Files are decoded with Pillow; fake or truncated images, HEIC/RAW, formats other than
JPEG/PNG/TIFF, images under 480 px on the short side and files over 50 MB are rejected
and nothing from that request is saved. Stored names are generated by the server (no
path traversal, no overwrites). Identical images are skipped. EXIF rotation is baked
into the pixels. Limits (5-200 images, 3 GB per job) live in `app/config.py`.

## Outputs (`outputs/<job_id>/`)

`final_mesh.ply` (cleaned, with vertex colours), `fused.ply` (dense point cloud),
`meshed-poisson.ply` (raw Poisson mesh, when it succeeded), `quality.json`,
`mesh_report.json`, `report.json`, `job.log`, `colmap.log`, `sparse_model/`.

## Failure reasons

A failed job stores `error_message`, `error_code` and `error_stage`. Codes include
`sparse_gate` (too few photos registered), `no_sparse_model`, `no_cuda`,
`too_few_points`, `colmap_failed`, `timeout`, `no_mesh`, `quality_failed`,
`missing_file`, `worker_interrupted`, `internal_error`.

## Configuration

Everything is in `app/config.py` and can be overridden in `.env` (see `.env.example`):
limits, dense-reconstruction quality (PatchMatch window/iterations, geometric
consistency, Poisson depth), mesh target size, thresholds, timeouts, CORS origins.

## Tests

```bash
pip install -r requirements-dev.txt
pytest -q
```

`tests/test_core.py` and `tests/test_api.py` need neither COLMAP nor a GPU (fake
database). `tests/test_mesh.py` needs Open3D and trimesh.

## Known limits (honest status)

- `/outputs` is still served publicly (`PUBLIC_OUTPUTS=true`) so existing frontends keep
  working. Switch it off once the frontend uses `/jobs/{id}/result/download`. There is no
  user authentication yet.
- The "largest component" step keeps the biggest connected piece of the mesh. If the
  table or background is larger than the object, it is kept. Object isolation before
  meshing is not implemented.
- Final meshes are not yet uploaded to Supabase storage; they stay on the worker's disk.
- The quality verdict uses simple, uncalibrated thresholds. There is no score yet.
- Matching is exhaustive (fine up to 200 images). Presets, video input, pre-flight
  image check and automatic retries with other parameters are not implemented.
- Only PLY output. Method 2 (AI/NeRF) does not exist.
